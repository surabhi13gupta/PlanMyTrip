The app in one page

From specs/goal-spec.md.

Problem: travelers scatter day-by-day plans across notes apps, spreadsheets and chats. PlanMyTrip gives them one place to plan a trip day by day and print a clean itinerary.

What a user can do (MVP)

  • Sign up and log in with a username and password
  • Add a trip: From and To dates, a destination, and a Trip Type (Solo, Couple, Family, Friends)
  • See all their trips on the home screen
  • Plan each day (Day 1 … Day N): add, edit, delete activities with a title, optional time and notes
  • Print the itinerary as a PDF, and edit or delete a trip

Rules that shape everything

  • A trip is at most 14 days and can't start in the past
  • Activities belong to a day number, so they move with the trip's dates
  • Shortening a trip warns before deleting activities on removed days
  • Closing the page logs you out; unsaved edits are saved first
  • Users only ever see their own trips

Screens follow your hand-drawn mockups in specs/mockups/: a home screen with a welcome and “Add new trip”, a “Plan a new trip” form, and a trip page with the days plus Print, Delete and Edit.

How the parts fit

Three parts: a frontend the user sees, a backend that enforces the rules, and a database that remembers everything.

Why a contract?

The frontend is TypeScript and the backend is Python, so they can't share code. Both follow api-contract-spec.md exactly, so they agree on every field name, rule and error.

The tools, explained

One line each on what the tool does in this project. Versions are what's installed now.

Frontend

  • React 19: builds screens from reusable pieces and redraws when data changes
  • TypeScript 6: JavaScript with types, so mistakes show in the editor
  • Vite 8: the dev server (instant reload) and the production build
  • Tailwind CSS 4: styling with small classes like bg-sand; our colors are defined once as tokens
  • Fira Sans: the font, bundled with the app (@fontsource)
  • oxlint: checks code for likely bugs (came with Vite's template)

Backend

  • FastAPI 0.142: maps URLs like /api/v1/health to Python functions
  • Pydantic 2: checks incoming data against rules; also reads settings
  • SQLAlchemy 2.1: talks to the database from Python
  • psycopg 3: the driver that actually connects to PostgreSQL
  • Alembic 1.20: migrations, versioned changes to the tables
  • uvicorn: runs the FastAPI app locally
  • pytest + ruff: tests, and linting/formatting

Infrastructure

  • Docker: runs PostgreSQL 16 in a disposable container on your machine
  • Vercel: hosts frontend and backend, deploys on every git push
  • Neon: hosted PostgreSQL, with a database copy per preview
  • GitHub: the master copy of the code and its history

Your machine

  • WSL (Ubuntu): the Linux system where the project lives
  • uv 0.12: Python packages and the project's own Python 3.14.8
  • Node 24 / npm 11: JavaScript runtime and packages
  • gh: GitHub CLI; also provides git's login
  • Docker Desktop: with WSL Integration on

One request, start to finish

What happens when you open http://localhost:5173. Every future feature follows the same path, just with more data.

  1. Browser

    Asks Vite for the page. Vite returns index.html and the JavaScript built from main.tsx and App.tsx.

  2. React · App.tsx

    The page appears showing “API: checking…”. Right after, useEffect runs fetch('/api/v1/health').

  3. Vite proxy · vite.config.ts

    The path starts with /api, so Vite forwards it to localhost:8000. The browser never knows a second server exists.

  4. FastAPI · main.py → health.py

    FastAPI matches /api/v1/health to the health() function and first calls get_db() for a database session.

  5. Database · db.py

    The session connects to PostgreSQL in Docker using DATABASE_URL from .env and runs SELECT 1, the smallest possible query.

  6. Response

    Success returns {"status": "ok"}. If the database fails, it returns status 503 with the contract's standard error shape.

  7. React

    The card updates: a dark blue dot and “API: ok”, or a red message explaining what's wrong.

On Vercel, only step 3 changes.

Instead of Vite's proxy, the rules in vercel.json send /api/… to the backend service, and the database is Neon instead of Docker.

Code walkthrough

Open each file to see the important part and what it does.

backend/app/main.py: the app and its URL prefix 
app = FastAPI(title="PlanMyTrip API", docs_url="/api/v1/docs", openapi_url="/api/v1/openapi.json")

api_v1 = APIRouter(prefix="/api/v1")
api_v1.include_router(health.router)
app.include_router(api_v1)

Creates the app and puts every route under /api/v1, as the contract requires. Vercel passes the full path (/api/v1/health) to the backend, so the same prefix works locally and hosted. The interactive docs live at /api/v1/docs.

backend/app/config.py: settings from the environment 
class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")

    database_url: str
    database_url_unpooled: str | None = None
    app_env: str = "development"

Reads settings from environment variables, or from backend/.env locally. Secrets never appear in code. On Vercel, the Neon integration supplies DATABASE_URL and DATABASE_URL_UNPOOLED.

to_sqlalchemy_url() turns postgresql://… (what Neon and Docker give) into postgresql+psycopg://… (what SQLAlchemy needs to pick the psycopg driver).

backend/app/db.py: connecting to the database 
return create_engine(
    get_settings().sqlalchemy_url,
    poolclass=NullPool,
    connect_args={"prepare_threshold": None},
)

NullPool: don't keep connections open between requests. On Vercel each function instance is short-lived, and Neon's own “pooler” shares connections instead.

prepare_threshold=None: turns off a psycopg speed trick (prepared statements) that Neon's pooler can't handle.

get_db() hands each request its own session and always closes it afterwards.

backend/app/routers/health.py: the first endpoint 
@router.get("/health")
def health(db: Annotated[Session, Depends(get_db)]):
    try:
        db.execute(text("SELECT 1"))
    except SQLAlchemyError:
        logger.exception("Health check could not reach the database")
        return error_response(503, "SERVICE_UNAVAILABLE", "The database can't be reached.")
    return {"status": "ok"}

Depends(get_db) is FastAPI's “dependency injection”: before running the function, FastAPI calls get_db() and passes in the session. Tests use this to swap in a broken database on purpose.

The error uses error_response() from errors.py, which produces the contract's shape: {"error": {"code", "message", "details"}}.

backend/alembic/: migrations

env.py tells Alembic which database to change: Neon's direct address on Vercel, Docker locally, or the test database during tests.

versions/0001_baseline.py is intentionally empty. It gives the Vercel build a migration to run, so we can confirm migrations work before any real tables exist. Step 2 adds 0002 with the users, sessions, trips and activities tables.

uv run alembic upgrade head    # apply all migrations not yet applied
uv run alembic current         # show which one the database is on (0001)
backend/tests/: how tests run

conftest.py points the app at planmytrip_test (never your development data), then runs all migrations once before the tests.

test_health.py checks three things: a healthy response, the 503 error when the database is unreachable, and a 404 for an unknown path.

backend/docker-compose.yml: the local database 
services:
  db:
    image: postgres:16
    environment: { POSTGRES_USER: planmytrip, POSTGRES_PASSWORD: planmytrip, POSTGRES_DB: planmytrip }
    ports: ["5432:5432"]
    volumes:
      - pgdata:/var/lib/postgresql/data
      - ./docker/init-test-db.sql:/docker-entrypoint-initdb.d/init-test-db.sql:ro

One PostgreSQL 16 container. Its data lives in a Docker “volume” (pgdata), so it survives restarts until you run docker compose down -v. The SQL file runs once, on first start, to create the test database. The password is only for your local machine.

frontend/vite.config.ts: plugins and the proxy 
plugins: [react(), tailwindcss()],
server: {
  proxy: { '/api': 'http://localhost:8000' },
},

The proxy makes the browser see one address in development, just like Vercel does in production. That's what will let the login cookie work later.

frontend/src/styles.css: colors and font as tokens 
@theme {
  --color-sand: #f4ece1;
  --color-primary: #1e3a5f;
  --color-muted: #6b5e4e;
  …
  --font-sans: 'Fira Sans', system-ui, sans-serif;
}

Defining colors in @theme creates Tailwind classes automatically: bg-sand, text-primary, border-line. Components use those names, never raw hex codes, so changing a color is one line.

frontend/src/App.tsx: the setup check page 
useEffect(() => {
  fetch(`${API_BASE_URL}/health`)
    .then(async (response) => {
      if (response.ok) { setApi({ kind: 'ok' }); return }
      const body = await response.json().catch(() => null)
      setApi({ kind: 'error', message: body?.error?.message ?? `HTTP ${response.status}` })
    })
    .catch(() => setApi({ kind: 'error', message: "Can't reach the API." }))
}, [])

The state has three possible values: checking, ok, or error with a message. If the API returns the standard error, its message is shown. If the API can't be reached at all, a fixed message is shown. This page is temporary; Step 3 replaces it with the real app.

vercel.json: two services, one address 
"services": {
  "frontend": { "root": "frontend/", "framework": "vite",
                "rewrites": [{ "source": "/(.*)", "destination": "/index.html" }] },
  "backend":  { "root": "backend/", "framework": "fastapi",
                "entrypoint": "app.main:app",
                "buildCommand": "uv run alembic upgrade head" }
},
"rewrites": [
  { "source": "/api/(.*)", "destination": { "service": "backend" } },
  { "source": "/(.*)",     "destination": { "service": "frontend" } }
]

The bottom rewrites decide which service gets each request. The frontend's own rewrite sends every page address to index.html, so React handles pages like /trips/42. The backend's buildCommand runs migrations during every deploy. Not yet tested on Vercel; that's the next step.

Glossary

Technical terms used in this guide and the specs. Product terms (Trip, Day, Activity) are in the goal spec's glossary.

TermMeaning
APIThe set of URLs the backend answers, like /api/v1/health. The frontend uses it to read and save data.
EndpointOne URL plus method, e.g. GET /api/v1/trips.
JSONThe text format for data sent between frontend and backend: {"status": "ok"}.
HTTP statusA number with each response: 200 ok, 201 created, 400 bad input, 401 not logged in, 404 not found, 503 unavailable.
ProxySomething that receives a request and forwards it elsewhere. Vite's proxy forwards /api to port 8000.
PortA numbered “door” on a computer: 5173 frontend, 8000 backend, 5432 database.
Environment variableA setting given to a program from outside its code, such as DATABASE_URL. Keeps secrets out of git.
MigrationA versioned script that creates or changes database tables, applied in order by Alembic.
ORMA library (SQLAlchemy) that lets Python code work with database rows as objects.
ContainerA sealed, disposable box running one program (here PostgreSQL), managed by Docker.
Virtual environmentA private folder of Python packages for this project (backend/.venv), managed by uv.
Lock fileThe exact version of every package (uv.lock, package-lock.json), so every machine installs the same code.
Serverless functionCode the host starts only when a request arrives. The backend runs this way on Vercel.
Preview deploymentA temporary copy of the app Vercel builds for each branch, with its own URL and, with Neon, its own database copy.
Session cookieA small value the browser sends automatically to prove you're logged in. httpOnly means page scripts can't read it.
BranchA separate line of work in git. setup-check holds the hello-world code until it's merged into main.
LintAutomatic checks for likely bugs and style problems (ruff, oxlint).
Dependency injectionFastAPI's Depends(...): it prepares what a function needs (like a database session) and passes it in.
