How the app is built, end to end
PlanMyTrip

A day-by-day trip planner: React in the browser, FastAPI on Vercel Functions, PostgreSQL on Neon, built spec-first.

The 30-second answer

PlanMyTrip is a full-stack web app where travelers plan a trip one day at a time, find ideas, see the weather, share a read-only link, and download the plan as a PDF. The frontend is a React 19 + TypeScript single-page app; the backend is a layered FastAPI REST API; data lives in PostgreSQL on Neon. Both halves deploy together as one Vercel project: every push builds a preview with its own database branch, and merging to main ships to production, with migrations running automatically during the build. Login uses server-side sessions in an httpOnly cookie, and every feature was written as a spec first and reviewed on a preview before merging.

    3 · Data

    Database tables

    Five tables in PostgreSQL, created and changed only through Alembic migrations, which run during every Vercel build.

    users

    • iduuid PK
    • usernameunique, lowercase
    • password_hashArgon2id
    • nameoptional

    Usernames are case-insensitive; the password itself is never stored.

    sessions

    • idSHA-256 of token
    • user_idFK → users
    • expires_at12 h idle

    Only the hash is stored, so a database leak gives no usable logins.

    trips

    • user_idFK → users
    • destinationtext ≤ 100
    • start/end_date≤ 14 days
    • trip_typesolo… friends
    • share_tokenunique, nullable

    Check constraints enforce the date rules in the database too.

    activities

    • trip_idFK → trips
    • day_number1…N
    • title≤ 100
    • timenullable
    • notes≤ 500

    Tied to a day number, not a date, so moving a trip's dates keeps the plan.

    idea_searches

    • query_keyunique
    • resultsjsonb
    • fetched_at30-day cache
    • fetched_bydaily limit

    Shared cache of SerpApi answers across all users and trips.

    A user has many sessions and trips; a trip has many activities. Deleting a user or a trip cascades. Migrations only add things (new tables, nullable columns), so the version still running keeps working during a deploy.

    5 · Cross-cutting concerns

    Security, reliability and cost

    Authentication

    • Server-side sessions: 32 random bytes in an httpOnly, Secure, SameSite=Lax cookie; the database stores only its SHA-256.
    • Passwords hashed with Argon2id. Wrong username and wrong password give the same error, with a dummy hash check, so timing doesn't reveal usernames.
    • Ends after 12 hours idle. Closing the tab also logs you out: a sessionStorage marker survives refresh but not closing, so the next visit logs out first.

    Authorization and CSRF

    • Every query filters by the current user. Someone else's trip returns 404, not 403, so IDs can't be probed.
    • CSRF: SameSite cookies, plus every write must send Content-Type: application/json, which a form on another site can't do. Otherwise it gets 415.
    • No CORS at all: the frontend and API share one origin.
    • Share links: 128 random bits, revocable, read-only shape, kept out of search engines and masked in logs.

    Serverless and data

    • Functions keep no state in memory; everything lives in Postgres.
    • SQLAlchemy uses NullPool with prepared statements off, because Neon's pooler (PgBouncer, transaction mode) does the pooling.
    • Migrations run in the build before the new code goes live. If one fails, the build stops and the old version stays up.
    • Unsaved edits are sent on pagehide with fetch(…, {keepalive: true}).

    Staying at $0

    • Ideas: results shared and cached for 30 days, 20 new searches per user per day, a 10 s timeout with no retry (a retry would spend another search), and an older saved answer as fallback.
    • Weather goes straight from the browser to Open-Meteo: no key, no server time.
    • The PDF is built in the browser, so there's no export endpoint.
    • An AI trip assistant was designed, then shelved because of its running cost.
    6 · How it was built

    Testing, tooling and workflow

    Spec-first workflow

    • Four specs in specs/: goal (features, user stories), frontend, backend, and the API contract.
    • Every change: update the spec, then build on a branch.
    • Each push creates a Vercel preview with its own Neon database branch; it's reviewed there, then merged by pull request.

    Frontend tests

    • Vitest + React Testing Library; the API is mocked at the network level with MSW.
    • Unit tests for pure helpers (dates, weather parsing, idea categories), component tests for forms, day cards, the Ideas panel, the Share dialog and pages.
    • TypeScript strict mode, oxlint.

    Backend tests

    • pytest with FastAPI's TestClient against a real PostgreSQL (Docker), migrated once per run.
    • Each test runs inside a transaction that's rolled back, so tests don't affect each other.
    • SerpApi is replaced by a fake: no real searches are spent. Ruff for lint and format; uv for packages.
    7 · Interview prep

    Questions you're likely to get

    Short answers you can say out loud, with the reasoning behind each choice.

    Walk me through the architecture.

    A React single-page app talks JSON to a FastAPI REST API, which stores data in PostgreSQL. Both are deployed as one Vercel project: Vercel's routing sends /api/* to the Python function and everything else to the static frontend, so they share one domain. The backend is layered: routers handle HTTP, services hold the business rules, and SQLAlchemy models talk to the database.

    Why React + FastAPI instead of one full-stack framework?

    A clear split between a typed UI and a typed API, each with its own validation (Zod and Pydantic) and tests. Python suits the backend logic and its tests against real Postgres. Vercel Services still deploys both together, so there's no CORS and only one deploy.

    How does login work? Why not a JWT in localStorage?

    Server-side sessions. Login creates a random token, stores its SHA-256 in a sessions table, and sets the token in an httpOnly cookie. JavaScript can't read the cookie, so an XSS bug can't steal it, and a session can be ended immediately by deleting its row. A JWT in localStorage is readable by scripts and hard to revoke.

    How do you protect against CSRF?
    • SameSite=Lax stops the cookie on most cross-site requests.
    • Every write must have Content-Type: application/json, which a plain HTML form can't send, and a cross-site script can't either without a CORS preflight that the API never allows. Writes without it get 415.
    How do you stop users seeing each other's trips?

    Every service query filters by the logged-in user's ID. A trip that isn't yours returns 404 rather than 403, so trip IDs can't be probed. Tests use a second user to check this on every endpoint.

    What changes when the backend runs serverless?
    • No in-memory state: sessions, caches and limits all live in Postgres.
    • Connections: NullPool with Neon's pooled URL, and prepared statements turned off because the pooler runs PgBouncer in transaction mode.
    • Cold starts are acceptable at this scale; the health endpoint helps check deployments.
    How do database migrations deploy safely?

    Alembic runs as the backend's build command, using Neon's direct connection, before the new code goes live. If it fails, the build stops and the old version keeps running. Migrations only add things (new tables, nullable columns), so the old code still works with the new schema. Preview builds migrate their own Neon database branch, never production.

    How does the Ideas feature avoid running costs?
    • SerpApi's free plan gives 250 searches a month, and its key stays on the server.
    • Answers are saved in idea_searches for 30 days and shared by every trip to the same place.
    • Each user gets 20 new searches a day; saved ones are free.
    • No retries, because a retry spends another search. If SerpApi fails, an older saved answer is used; with none, the panel offers a Google Maps link instead.
    Why call Open-Meteo from the browser but SerpApi from the server?

    SerpApi needs a secret key and has a small quota, so it must sit behind the server, which also caches and rate-limits it. Open-Meteo needs no key and has generous free limits, so calling it from the browser saves server time and code. If it fails, the weather is simply hidden.

    How are share links kept safe?
    • Codes are 128 random bits (secrets.token_urlsafe(16)), so they can't be guessed.
    • The public endpoint returns a reduced shape with no IDs or owner.
    • It sends Cache-Control: no-store, so turning a link off works at once, and noindex for search engines.
    • Codes are masked in request logs. Turning a link off deletes the code; sharing again makes a new one.
    How do you manage state on the frontend?

    Server data lives in TanStack Query. After any change, the app invalidates the trip query and refetches, so nothing is shown that the server hasn't confirmed. UI state is plain useState. There's no global store; the logged-in user is just the ['me'] query.

    How do you validate input?

    Twice, from one contract. Zod schemas give instant feedback in forms; Pydantic validates again on the server, with the same messages. The API contract spec defines every rule, for example the 14-day limit, no start date in the past, and title length. Date rules are also database check constraints.

    How is the PDF made?

    In the browser with @react-pdf/renderer, built from the same trip data the page already has. The library is large, so it's only loaded when the user clicks Print. The PDF has clickable Google Maps links on every activity.

    How is it tested?
    • Backend: pytest against real Postgres. Each test runs in a transaction that's rolled back. Outside services are faked.
    • Frontend: Vitest and React Testing Library, with MSW mocking the API at the network level.
    • Every feature is also checked by hand on its Vercel preview before merging.
    What happens if a user closes the tab with unsaved changes?

    On pagehide, every open form with valid unsaved changes is sent with fetch(…, {keepalive: true}), which finishes after the page is gone. The session is still valid then, because logout only happens on the next visit.

    What would you improve next?
    • CI with GitHub Actions to run both test suites on every pull request.
    • Rate limiting failed logins, with counts stored in Postgres.
    • Playwright end-to-end tests (already written, parked).
    • Error monitoring and structured logs.
    • Features: packing list, calendar export, a "today" view, installable PWA.
