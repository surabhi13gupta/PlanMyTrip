# Backend Spec — PlanMyTrip

> Status: Draft | Owner: Surabhi Gupta | Last updated: 2026-10-04
> Related: [goal-spec.md](./goal-spec.md), [frontend-spec.md](./frontend-spec.md), [api-contract-spec.md](./api-contract-spec.md)

## 1. Overview
<!-- Responsibilities of the backend. -->
The backend is a REST JSON API that:
- creates accounts, logs users in and out, and keeps track of who is logged in with a session cookie;
- stores trips and their activities in PostgreSQL, and lets each user see and change only their own data;
- enforces every product rule from [goal-spec.md](./goal-spec.md), even if the frontend is skipped (for example, by calling the API directly): the 14-day maximum, start date not in the past, and activities belonging to valid day numbers.

The backend does **not** generate PDFs; the browser does that (see [frontend-spec.md](./frontend-spec.md)).

Terms such as Trip, Day, and Activity are used as defined in the Glossary in [goal-spec.md](./goal-spec.md#13-glossary).

## 2. Tech Stack
- Language / runtime: Python 3.12
- Framework: FastAPI
- Validation: Pydantic v2 (built into FastAPI)
- Database: PostgreSQL, hosted on Neon
- ORM / query layer: SQLAlchemy 2.0 (synchronous) with the `psycopg` (v3) driver
- Database migrations: Alembic
- Password hashing: Argon2id, through `argon2-cffi`
- Caching: None. Not needed at this scale.
- Background jobs / queues: None
- Package manager: `uv`
- Linting / formatting: Ruff
- Testing: pytest + FastAPI's `TestClient`, against a real local PostgreSQL
- Hosting: Vercel Functions, in the same Vercel project as the frontend (section 14)

## 3. Architecture
One FastAPI app, organized in layers. Each layer only calls the one below it:

```
HTTP request
   │
   ▼
Routers (app/routers/)        – URL paths, request/response models, status codes
   │
   ▼
Services (app/services/)      – business rules: ownership, 14-day limit, shortening trips
   │
   ▼
Models + DB session (app/models/, app/db.py) – SQLAlchemy tables and queries
   │
   ▼
PostgreSQL (Neon)
```

- **Routers** handle HTTP only: read the request, call a service, and return the response.
- **Services** hold all the rules, so they can be tested without HTTP.
- **Dependencies** (FastAPI `Depends`) provide the database session and the current user to each router.
- All routes are under the `/api/v1` prefix, both locally and on Vercel.
- **Imports:** Code inside `backend/app/` uses relative imports (`from .db import get_db`), so the same code runs locally (`uvicorn app.main:app` from `backend/`) and on Vercel (imported as `backend.app.main` by `api/index.py`).
- **Serverless:** On Vercel, the app runs as a function that starts when requests arrive and stops when idle. The app therefore keeps no state in memory between requests; everything lives in PostgreSQL.

## 4. Data Model
All tables except `login_attempts` use UUID primary keys, generated by the app. Timestamps are stored as `timestamptz` (UTC).

### 4.1 users
| Field | Type | Constraints | Description |
|-------|------|-------------|-------------|
| id | uuid | PK | |
| username | varchar(30) | not null, unique | Always stored in lowercase, so usernames are case-insensitive |
| password_hash | text | not null | Argon2id hash; the password itself is never stored |
| created_at | timestamptz | not null, default now() | |
| updated_at | timestamptz | not null, default now() | |

### 4.2 sessions
| Field | Type | Constraints | Description |
|-------|------|-------------|-------------|
| id | char(64) | PK | SHA-256 hash of the session token. The token itself is only in the user's cookie, so a database leak doesn't expose usable sessions |
| user_id | uuid | not null, FK → users.id, on delete cascade | |
| created_at | timestamptz | not null, default now() | |
| expires_at | timestamptz | not null | |

### 4.3 trips
| Field | Type | Constraints | Description |
|-------|------|-------------|-------------|
| id | uuid | PK | |
| user_id | uuid | not null, FK → users.id, on delete cascade | The owner |
| name | varchar(100) | not null | |
| destination | varchar(100) | not null | Free text, e.g. "Paris, France" |
| start_date | date | not null | Calendar date, no time zone |
| end_date | date | not null, check `end_date >= start_date`, check `end_date - start_date <= 13` | At most 14 days, counting both dates |
| trip_type | varchar(10) | not null, check in (`solo`, `couple`, `family`, `friends`) | |
| created_at | timestamptz | not null, default now() | |
| updated_at | timestamptz | not null, default now() | |

### 4.4 activities
| Field | Type | Constraints | Description |
|-------|------|-------------|-------------|
| id | uuid | PK | |
| trip_id | uuid | not null, FK → trips.id, on delete cascade | |
| day_number | smallint | not null, check `day_number >= 1` | Day 1 is the trip's start date. Must also be ≤ the trip's length (checked by the service, because it depends on the trip's dates) |
| title | varchar(100) | not null | |
| time | time | null | Local time at the destination; null means "no time" |
| notes | varchar(500) | null | |
| created_at | timestamptz | not null, default now() | Also used to order activities without a time |
| updated_at | timestamptz | not null, default now() | |

### 4.5 login_attempts
| Field | Type | Constraints | Description |
|-------|------|-------------|-------------|
| id | bigint | PK, identity | |
| username | varchar(30) | not null | Lowercased, as typed (may not be a real account) |
| attempted_at | timestamptz | not null, default now() | |

Only failed logins are recorded. Rows older than 1 day are deleted whenever a new attempt is recorded.

### Relationships
- A user has many trips; a trip belongs to one user.
- A trip has many activities; an activity belongs to one trip.
- A user has many sessions.
- Deleting a user deletes their sessions, trips, and activities. Deleting a trip deletes its activities.

### Indexes
- `users.username`: unique
- `sessions.user_id`
- `trips (user_id, start_date)`: lists a user's trips in date order
- `activities (trip_id, day_number)`: loads a trip's plan
- `login_attempts (username, attempted_at)`

## 5. Business Logic / Services
| Service | Responsibilities | Key Rules |
|---------|------------------|-----------|
| `auth_service` | Sign up, log in, log out, look up the current user | Usernames lowercased before saving and comparing. Signup with a taken username → 409 `USERNAME_TAKEN`. Wrong username **or** password → the same 401 `INVALID_CREDENTIALS`, and a dummy hash check runs when the user doesn't exist, so response timing doesn't reveal which usernames exist |
| `session_service` | Create, look up, renew, and delete sessions | A new session lasts 7 days. On each request, if less than 6 days remain, `expires_at` is pushed back to 7 days from now (so it is written at most once a day). Expired sessions are treated as missing and deleted when found |
| `trip_service` | List, create, read, update, and delete trips | Every query filters by the current user; another user's trip is "not found" (404), never "forbidden", so trip IDs can't be probed. See the trip rules below |
| `activity_service` | Create, update, and delete activities | The trip must belong to the current user. `day_number` must be between 1 and the trip's length. Activities are returned sorted: those with a time first, by time; then those without, by `created_at` |

**Trip rules**
- **Start date not in the past:** On create, and on update when `start_date` changes, the start date must be no earlier than *today*. "Today" is judged by the user's local date, which the server doesn't know, so the server accepts any date ≥ (today in UTC − 1 day). The frontend enforces the exact local-date rule.
- **Length:** `end_date ≥ start_date` and the trip is at most 14 days. Also enforced by database check constraints.
- **Shortening a trip:** When an update makes the trip shorter, activities with `day_number` greater than the new length would be removed.
  - If there are any and the request does not include `"confirmDeleteActivities": true`, the update is rejected with 409 `ACTIVITIES_WOULD_BE_DELETED`, including the number of affected activities in `details`. Nothing changes.
  - If the request confirms, the trip update and the activity deletion happen in **one database transaction**.
  - Moving the dates without changing the length deletes nothing, because activities are tied to day numbers.
- **Delete:** Deleting a trip deletes its activities (database cascade).

## 6. Authentication & Authorization
- **Auth method:** Server-side sessions stored in the `sessions` table, identified by a cookie.
- **Session token:** 32 random bytes from Python's `secrets` module, URL-safe encoded. The cookie holds the token; the database holds its SHA-256 hash.
- **Cookie:** name `session`, `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age` 7 days, and `Secure` everywhere except local development (local runs on plain `http://localhost`).
- **Password hashing:** Argon2id with `argon2-cffi`'s default settings. Passwords must be 8–72 characters (same limit as the frontend).
- **Token lifetime / refresh:** 7 days, renewed while the user stays active (section 5).
- **Logout:** Deletes the session row and clears the cookie. The session stops working immediately.
- **Roles & permissions:** None. Every user has the same abilities.
- **Resource ownership rules:** A user can only see and change their own trips and those trips' activities. This is checked in the service layer on every request, by filtering on `user_id`.
- **CSRF protection:** `SameSite=Lax` stops the cookie being sent on most requests that start on other websites. In addition, every request that changes data (POST, PATCH, DELETE) must have `Content-Type: application/json`, which an ordinary form on another website can't send. Requests without it get 415.
- **Login rate limiting:** After 10 failed logins for the same username within 15 minutes, further attempts for that username get 429 `TOO_MANY_ATTEMPTS` until the window passes. Stored in `login_attempts` (an in-memory counter wouldn't work, because serverless functions don't share memory). Trade-off: someone who knows a username could keep that account locked by repeatedly failing; this is acceptable for the MVP.

## 7. External Integrations
| Service | Purpose | Failure Handling |
|---------|---------|------------------|
| Neon (PostgreSQL) | Stores all data | If the database can't be reached, requests return 503 `SERVICE_UNAVAILABLE` and the error is logged. A paused Neon database wakes up automatically on the first request, which may take a moment longer |

No other third-party services in the MVP.

## 8. Validation
- **Input validation approach:** Every request body is a Pydantic model with the same rules as the frontend's Zod schemas ([frontend-spec.md §9](./frontend-spec.md#9-forms--validation)). The API contract is the single source of truth for those rules; both sides follow it. Text fields are trimmed before checking their length.
- **Rules that need the database** (username taken, day number within the trip, shortening a trip) are checked in the services.
- **JSON naming:** The API uses camelCase (`startDate`, `dayNumber`), matching TypeScript; the Python code uses snake_case. Pydantic's `alias_generator=to_camel` converts between them.
- **Shared schemas with frontend?** No, they can't be shared across languages. The API contract keeps them in sync, and both sides have tests for the key rules.

## 9. Error Handling
- **Error format:** Every error uses the standard format in [api-contract-spec.md](./api-contract-spec.md#2-standard-error-response): `{ "error": { "code", "message", "details" } }`.
- **Validation errors:** FastAPI's default 422 response is replaced with 400 `VALIDATION_ERROR`, with one `details` entry per field (`field` in camelCase, plus `message`), so the frontend can show each error on its field.
- **Unexpected errors:** Return 500 `INTERNAL_ERROR` with a generic message. The full error is logged, never sent to the client.
- **Logging of errors:** 4xx are logged at `INFO`, 5xx at `ERROR` with the stack trace.

## 10. Security
- **CORS:** Not enabled. The frontend and API share one address (on Vercel and through the Vite proxy locally), so browsers never make cross-origin requests to the API.
- **Rate limiting:** Login only, as in section 6. Vercel also provides basic protection against floods of traffic.
- **Secrets management:** `DATABASE_URL` and other secrets live in Vercel's environment variable settings and in a local `.env` file that is listed in `.gitignore`. Secrets never go in the code or on GitHub.
- **SQL injection:** All queries go through SQLAlchemy with bound parameters; no SQL is built by joining strings.
- **XSS:** The API returns JSON only. React escapes text when showing it, so an activity titled `<script>` appears as text.
- **Sensitive data in logs:** Passwords, cookies, and session tokens are never logged.
- **Accounts:** Two-factor authentication is turned on for the GitHub, Vercel, and Neon accounts.

## 11. Configuration & Environment
| Variable | Description | Required | Default |
|----------|-------------|----------|---------|
| `DATABASE_URL` | Neon **pooled** connection string, used by the app | Yes | — |
| `DATABASE_URL_UNPOOLED` | Neon direct connection string, used only by Alembic migrations | Yes (for migrations) | — |
| `APP_ENV` | `development`, `preview`, or `production` | No | `development` |
| `SESSION_COOKIE_SECURE` | Adds `Secure` to the cookie | No | `false` in development, `true` otherwise |
| `SESSION_TTL_DAYS` | Session lifetime in days | No | `7` |
| `LOG_LEVEL` | Logging level | No | `INFO` |

The Vercel–Neon integration sets `DATABASE_URL` and `DATABASE_URL_UNPOOLED` automatically.

**Database connections on serverless:** The app connects through Neon's pooled address, and SQLAlchemy uses `NullPool` (no connection pool inside the function, because Neon's pooler does that job). `psycopg` prepared statements are turned off (`prepare_threshold=None`), as Neon's pooler requires.

## 12. Logging & Monitoring
- **Logging format / levels:** Python `logging` to standard output, one line per request: method, path, status, duration, and a request ID. Vercel collects standard output and shows it under the project's Logs tab.
- **Health check endpoint:** `GET /api/v1/health` → `200 {"status": "ok"}` if the database answers a `SELECT 1`, otherwise 503.
- **Metrics / tracing:** None beyond Vercel's built-in dashboard in the MVP.

## 13. Testing Strategy
- **Unit:** Services, especially: trip length and start-date rules, the "today − 1 day" allowance, shortening with and without confirmation, day-number range checks, activity sorting, and username lowercasing.
- **Integration:** Every endpoint, through FastAPI's `TestClient`, against a real PostgreSQL. Must include:
  - **Ownership:** user B gets 404 for user A's trip and activities, for every endpoint
  - The signup → login → me → logout cycle, and that the session stops working after logout
  - Rate limiting after 10 failed logins
  - Validation errors returned as 400 with field details
- **Test database / fixtures:** A separate `planmytrip_test` database in the local PostgreSQL (Docker). Alembic migrations run once per test session; each test runs inside a transaction that is rolled back afterwards, so tests don't affect each other. Fixtures create logged-in users and sample trips.

## 14. Deployment
- **Environments:**
  - **Development:** Your computer. FastAPI with `uvicorn --reload` on `localhost:8000`, PostgreSQL 16 in Docker (`docker compose up db`). The Vite dev server sends `/api` requests to port 8000.
  - **Preview:** Every branch and pull request on Vercel. With the Neon integration's "database branch for each preview deployment" option turned on, each preview gets its own copy of the database, so testing on a preview can't touch real data.
  - **Production:** Pushes to `main`.
- **Hosting:** Vercel, in **one project** with the frontend. The repository root is the project root:
  - `api/index.py` is the Vercel Function entry point. It only imports the FastAPI app: `from backend.app.main import app`.
  - The root `vercel.json` builds the frontend and sends all `/api/*` requests to that function:
    ```json
    {
      "buildCommand": "cd frontend && npm ci && npm run build",
      "outputDirectory": "frontend/dist",
      "rewrites": [
        { "source": "/api/(.*)", "destination": "/api/index" },
        { "source": "/(.*)", "destination": "/index.html" }
      ],
      "functions": {
        "api/index.py": { "excludeFiles": "{frontend/**,backend/tests/**}" }
      }
    }
    ```
  - Vercel installs the function's Python packages from the root `requirements.txt`, which is generated from `backend/pyproject.toml` with `uv export --no-dev -o requirements.txt`. Regenerate it whenever dependencies change.
  - **First implementation step:** deploy a "hello world" version (the health endpoint plus a blank React page) to check this setup works end to end before building features.
- **CI/CD:** Vercel deploys automatically on every push. Tests run locally before pushing; adding GitHub Actions to run them on every push is a post-MVP option.
- **Database migrations:** Alembic, run by hand: `alembic upgrade head` against `DATABASE_URL_UNPOOLED`, before pushing code that needs the new tables. Migrations only ever add things, or are written so the code currently running keeps working, so the order of deploy and migration doesn't break the live app.
